# Роли, команды и управление пользователями — дизайн

Дата: 2026-09-10

> **Пересмотрено 2026-09-11.** §1.4 отменяет прежнее решение «без обязательной команды» — теперь
> команда создаётся всегда. Добавлен раздел 1.5 о жизненном цикле приглашений. Остальные разделы
> актуальны без изменений; расхождения с текущим кодом (если появятся) фиксируются отдельными
> ревизиями, а не правкой этого файла задним числом.

## Контекст

Изначальный баг-репорт: в админке (`/admin/stats`) видно 2 артефакта и 2 агента, но
разделы «Артефакты»/«Агенты» показывают пустые списки. Root cause: `/admin/stats`
считает объекты глобально по всему инстансу, а списки строго скоуплены на
`orgId` текущей команды, при этом селектор команд в сайдбаре может предложить
только те команды, где у пользователя есть членство (`org_members`) — у
суперадмина это обычно только его личная (пустая) команда.

По ходу обсуждения задача выросла из точечного фикса в переработку модели
ролей, отвязку пользователей от обязательного членства в команде и два новых
раздела UI. Ниже — согласованный дизайн всего этого целиком.

## 1. Модель данных и роли

### 1.1 Суперадмин

- `users.isSuperadmin: boolean` остаётся как есть — единственный глобальный
  признак роли, не привязанный ни к одной команде.
- Ровно один суперадмин в системе, задаётся один раз при сиде
  (`seedSuperadmin`), **не может быть передан** другому пользователю и не может
  быть удалён/разжалован через UI. Никакого эндпоинта на смену этого флага не
  добавляется.
- Суперадмин (как и любой другой пользователь) может сменить свой email и
  пароль через новый универсальный эндпоинт `PATCH /auth/me` (см. 2.4).

### 1.2 Роли внутри команды

- Остаются как есть: `owner` / `admin` / `member` / `viewer` в таблице
  `org_members` (`orgRoleSchema` в `@open-artifacts/shared`). `owner` и `admin`
  по-прежнему равны в правах на управление командой (приглашение/удаление
  участников).
- Роль **привязана к паре `(orgId, userId)`**, а не к пользователю глобально —
  это уже так работает: один и тот же пользователь может быть `owner` в одной
  команде, `admin` в другой и `member`/`viewer` в третьей.
- Новое: возможность сменить роль **уже существующего** участника (сейчас
  такого эндпоинта нет — роль можно задать только в момент инвайта). См.
  `PATCH /orgs/:id/members/:userId` в разделе 2.1.
  - Разрешено `owner`/`admin` этой команды или суперадмину.
  - Нельзя разжаловать последнего оставшегося `owner` команды (в команде
    всегда должен быть хотя бы один owner).

### 1.3 Статус учётной записи пользователя

- Новое поле `users.status: 'active' | 'blocked' | 'deleted'`, default
  `'active'`. Заменяет жёсткое удаление — консистентно с уже существующим
  soft-delete у артефактов (`deletedAt`).
- Логин (`POST /auth/login` и т.п.) отклоняется, если `status !== 'active'`.
- `blocked` — обратимая блокировка, учётная запись остаётся видна в списках.
- `deleted` — soft-delete: пользователь перестаёт быть виден в обычных списках
  (кроме `GET /admin/users`, где виден с пометкой), при удалении также
  каскадно удаляются все его строки в `org_members` (теряет доступ ко всем
  командам). Данные, которые он создал (артефакты, агенты, записи audit log),
  не трогаются — `ownerId`/`actorId` просто продолжают указывать на
  «удалённого» пользователя.
- Суперадмина нельзя заблокировать/удалить (эндпоинт должен это проверять).

### 1.4 Основное пространство создаётся всегда (пересмотрено 2026-09-11)

Отменяет прежнее решение «без обязательной команды» — на практике оно оставляло
нового пользователя в пустоте: пустой переключатель команд, недоступные
артефакты, экран без следующего шага.

- Каждый пользователь **всегда** получает ровно одно авто-созданное
  «основное» пространство (`orgs.kind = 'main'`) — при самостоятельной
  регистрации и при регистрации по invite-ссылке одинаково. `registerUser`
  (`apps/api/src/services/users.ts`) создаёт пользователя и его основное
  пространство в одной транзакции.
- Регистрация по invite-ссылке добавляет **второе** членство — в пригласившей
  команде, с ролью из инвайта. Основное пространство создаётся всегда, вне
  зависимости от инвайта.
- Основное пространство — обычная команда с точки зрения возможностей: в неё
  можно приглашать людей, её можно переименовать. Отличие ровно одно:
  создатель (`orgs.createdBy`) не может её покинуть и не может быть из неё
  удалён — у неё нет модели передачи владения.
- Имя у всех основных пространств одинаковое («Основное пространство»,
  задаётся на сервере) — различение сознательно вынесено на уровень UI
  (единый компонент `OrgIdentity`: цвет от `org.id`, бейдж «Основное», вторая
  строка — владелец/slug), а не в данные.
- Существующие до этой ревизии команды уже зарегистрированных пользователей
  не трогаем и не мигрируем — миграция снабжает основным пространством только
  тех, у кого на момент миграции не было ни одного членства; у кого было —
  их команды остаются как есть (`kind='team'` по умолчанию колонки).

### 1.5 Жизненный цикл приглашения (добавлено 2026-09-11)

Приглашение — не «письмо и всё», а состояние с явными переходами:
`pending → accepted | declined | revoked`. Истечение (`expiresAt`) не хранится
отдельным статусом — в проекте нет планировщика, поэтому оно всегда
вычисляется на лету из `expiresAt`, а не поддерживается фоновой задачей.

- **Создание/перевыпуск** — `POST /orgs/:id/invites` одновременно и создаёт
  новое приглашение, и перевыпускает уже существующее pending-приглашение на
  тот же `(orgId, email)` (новый токен, новый срок — старая ссылка
  немедленно перестаёт работать). Отдельного `/resend` нет: у перевыпуска и
  так нет иной семантики. Ответ включает `accountExists`, чтобы интерфейс
  показал верную подсказку: «отправьте ссылку» для нового адреса или «он
  увидит приглашение в интерфейсе» для существующего аккаунта.
- **Публичный превью** — `GET /invites/:token`, без авторизации: отдаёт
  название команды, роль, имя пригласившего и **маскированный** email
  (`i***n@example.com`). Полный email и признак «есть ли аккаунт» сюда
  сознательно не попадают — токен может утечь (реферер, скриншот, чат), и
  оба поля превратили бы публичную страницу в оракул для перебора адресов.
- **Принятие/отклонение существующим пользователем** — `POST
  /invites/:token/accept` и `/decline`, только для авторизованного
  пользователя. Авторизация всегда проверяется по живому
  `invites.email === текущий email пользователя`, а не по денормализованному
  `invitedUserId` — так поведение остаётся верным, даже если приглашённый
  успел сменить email.
- **Обнаружение** — так как в проекте нет отправки почты, единственный канал,
  которым уже зарегистрированный пользователь узнаёт о приглашении, — раздел
  «Приглашения» (`/invites`, `GET /invites/me`) и счётчик в `/auth/me`.
- **Регистрация по инвайту** обязана использовать email из самого
  приглашения, а не из тела запроса: расхождение — это `400
  invite_email_mismatch`, а не молчаливая подмена (иначе человек получил бы
  аккаунт на адрес, который не вводил и не контролирует). Веб-форма поэтому
  не отправляет email вовсе для этого пути — сервер берёт его из инвайта.

## 2. API

Везде, где ниже упоминаются `page`/`pageSize`: `page` 1-based (default `1`),
`pageSize` default `20`, максимум `100`. Ответ пагинированных списков — плоский
объект с `total` (общее число записей) в дополнение к самому массиву, без
отдельной обёртки `meta`.

### 2.1 Команды (`apps/api/src/routes/orgs.ts`)

- `GET /orgs?search=&page=&pageSize=` — заменяет текущий безлимитный `GET
  /orgs` и убираемый `GET /admin/orgs`.
  - Обычный пользователь: пагинированный список **его** команд (по
    `org_members`), с поиском по названию.
  - Суперадмин: пагинированный список **всех** команд системы, с поиском.
  - Ответ: `{ orgs: [{ id, name, slug, role | null, memberCount }], total,
    page, pageSize }`. `role` — роль текущего юзера в этой команде, `null` для
    суперадмина, если он не состоит в ней.
- `GET /orgs/:id` — новый, для карточки одной команды: `{ id, name, slug,
  storageQuotaBytes, memberCount, createdAt, myRole | null }`. Доступ: участник
  команды или суперадмин.
- `POST /orgs` — без изменений (создатель становится `owner`).
- `GET /orgs/:id/members` — без изменений.
- `PATCH /orgs/:id/members/:userId` — новый. Body: `{ role }`. Разрешено
  `owner`/`admin` этой команды или суперадмину. 400/409, если это последний
  `owner` и его пытаются понизить.
- `POST /orgs/:id/invites`, `DELETE /orgs/:id/members/:userId` — без
  изменений в логике, но теперь доступны суперадмину для **любой** команды
  (уже работает через `requireOrgRole`, т.к. он возвращает `"owner"` для
  `isSuperadmin`).

### 2.2 Артефакты и агенты

- `GET /artifacts`, `GET /agents`: `orgId` остаётся опциональным query-параметром.
  - С `orgId` — поведение не меняется (список одной команды).
  - Без `orgId`:
    - identity = агент (API-ключ) — не меняется, `orgId` берётся из ключа,
      параметр всё ещё обязателен по факту.
    - identity = обычный пользователь — возвращается объединённый список по
      **всем его командам** (новые `listArtifactsForOrgs(db, orgIds[])` /
      `listAgentsForOrgs(db, orgIds[])`, `orgIds` = все `org_members.orgId`
      этого юзера).
    - identity = суперадмин — возвращается список **по всем командам
      системы** (`listAllArtifacts(db)` / `listAllAgents(db)`, без фильтра по
      `orgId`).
  - Ответ не меняется по форме — каждая запись уже содержит `orgId`, фронт
    использует его для колонки «Команда» и клиентской фильтрации.

### 2.3 Пользователи (`apps/api/src/routes/admin.ts`, только суперадмин)

- `GET /admin/users?search=&page=&pageSize=` — пагинированный список всех
  пользователей: `{ id, email, name, status, isSuperadmin, createdAt, orgs:
  [{ orgId, orgName, role }] }`.
- `PATCH /admin/users/:id/status` — body `{ status: 'active'|'blocked'|'deleted'
  }`. Запрещено применять к суперадмину.
- Смена роли пользователя в конкретной команде из этого раздела переиспользует
  `PATCH /orgs/:id/members/:userId` — отдельного дублирующего эндпоинта не
  создаём.
- `GET /admin/orgs` — удаляется, заменён на `GET /orgs` (см. 2.1).

### 2.4 Аккаунт

- `PATCH /auth/me` — новый, доступен любому аутентифицированному пользователю
  (включая суперадмина) для смены **своего** email и/или пароля. Требует
  подтверждения текущим паролем.

## 3. Frontend/UX

### 3.1 Сайдбар (`apps/web/src/components/Layout.tsx`)

- Селектор команды получает первым пунктом **«Все организации»**
  (`currentOrgId = "all"`), затем список команд из пагинированного `GET
  /orgs` (первая страница; при необходимости — подгрузка следующих при
  скролле/поиске, без отдельного полноценного комбобокса на первом этапе).
- Для обычного пользователя «Все» = сумма его команд, для суперадмина = вообще
  все команды системы, включая те, где он не состоит.

### 3.2 Артефакты / Агенты

- `currentOrgId === "all"`: запрос идёт без `orgId`, в таблице добавляется
  колонка «Команда» (по `orgId` записи → имя ищется в уже загрученном списке
  команд), плюс собственный **внутристраничный** фильтр (select с поиском) —
  позволяет сузить до одной команды, не трогая сайдбар.
- Форма создания артефакта/агента скрыта в режиме «Все» — создание требует
  выбранной конкретной команды.
- Сообщение-заглушка при отсутствии команд меняется на актуальное и ссылается
  на раздел «Команды».

### 3.3 «Команды» (было `OrgPage` / «Команда», двухуровневый)

- Уровень 1, `/teams`: таблица команд (поиск, пагинация), скоуп по роли (свои
  — обычный юзер, все — суперадмин), кнопка «Создать команду».
- Уровень 2, `/teams/:id`: карточка команды — метаданные, список участников с
  ролями (смена роли inline, если есть права), форма приглашения, удаление
  участника, кнопка «Покинуть команду» для себя.

### 3.4 «Пользователи» (новый пункт меню, только для `me.isSuperadmin`)

- Таблица всех пользователей: поиск, пагинация, для каждого — статус
  (active/blocked/deleted, со сменой inline) и список его команд с ролями
  (смена роли inline через `PATCH /orgs/:id/members/:userId`).
- Действие «Удалить»/«Заблокировать» учётной записи — с подтверждением,
  недоступно для суперадмина.

## 4. Вне рамок (сознательно не делаем)

- Миграцию/чистку существующих личных команд уже зарегистрированных
  пользователей.
- Комбобокс с server-side поиском по всем командам системы в сайдбаре —
  первая страница пагинированного списка достаточна для MVP.
- Публичные/discoverable команды (вступление без приглашения) — вне скоупа.
- Восстановление удалённого (`deleted`) пользователя через UI — только
  active ⇄ blocked туда-обратно; `deleted` считается терминальным на этом
  этапе.

## 5. Тестирование

- Ручная проверка в докере: суперадмин без явного выбора команды видит все
  артефакты/агентов сразу («Все» по умолчанию); переключение на конкретную
  команду сужает список; обычный пользователь видит только свои команды и не
  видит пункт «Пользователи».
- Автотесты (если в проекте есть тестовый раннер — проверить) на: смену роли
  участника (включая защиту последнего owner), блокировку/удаление
  пользователя (логин отклоняется), регистрацию без invite (юзер без команд),
  регистрацию по invite (юзер сразу в команде), пагинацию `/orgs` и
  `/admin/users`.
